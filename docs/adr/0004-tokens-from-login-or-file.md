# The connector gets tokens from a browser login or a file, never from a command

A token source is either `login: browser` (PKCE, refresh token in the OS keychain per environment) or `file` (re-read on every connection or request, raw JWT or a JSON field), and connect.yaml cannot name a command to run. Running a configured command would turn a config file into code execution on every connection, and a file covers the other producers: whatever refreshes the token (an agent runtime, a sidecar) writes it, and a status file next to it explains a missing or expired token to the person or agent reading the error. A token problem fails only the connection or request that hit it, never the connector.

The connector's local ports serve ClickHouse clients, never web pages. Any page the user opens can make the browser send a request to `127.0.0.1`, and a host name the page controls can be rebound to `127.0.0.1`; since the connector adds the user's token to whatever it forwards, such a request would run as the user, and with `add_http_cors_header` the page could read the answer. So the HTTP port refuses with 403, before it reads a token, every request that carries `Origin`, or `Sec-Fetch-Site` other than `none`, or a `Host` that is not `localhost` or a loopback IP literal with the listener's port; it removes `add_http_cors_header`, never forwards `Origin`, `Sec-Fetch-*`, `Referer` or `Cookie`, and drops `Access-Control-*` from answers (serve removes the parameter and those headers too). Plain HTTP clients send none of these headers. The HTTP port also never starts a browser login: without a stored login it answers 401 and names `chauth login <env>`; the native port, which a browser cannot speak, logs in on first use.
